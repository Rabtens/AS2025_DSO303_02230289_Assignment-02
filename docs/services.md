# Task 2 – Service documentation

Every service in the design, with the alternative it was chosen over and its key configuration (as built in [infra/](../infra/)).

| Service | Role | Why over an alternative | Key configuration | Connects to |
|---|---|---|---|---|
| **Amazon Route 53** | DNS for the exam site (alias record to CloudFront) | Alias records to CloudFront are free of query charge and health-aware; third-party DNS cannot alias to AWS resources at the zone apex | Public hosted zone; `A` alias to the distribution; optional in the lab (`domain_name` + `hosted_zone_id`), default CloudFront domain otherwise | CloudFront, ACM |
| **AWS Certificate Manager** | TLS certificate for the custom domain | Free, auto-renewing public certs; buying and rotating certs by hand risks an expired cert during exams | DNS-validated in us-east-1; TLS 1.2+ (`TLSv1.2_2021`) | Route 53, CloudFront |
| **AWS WAF** | Blocks common attacks and abusive clients at the edge | Stops bad traffic before it consumes Lambda/DB capacity; a self-run proxy needs patching and scaling | Common + Known-Bad-Inputs managed rule groups; rate rule 100,000 requests / 5 min / IP (high because campuses share NAT IPs); metrics on | CloudFront |
| **Amazon CloudFront** | CDN, single entry point, routes `/*` to S3 and `/api/*` to the API | Serves the 3,000-student burst from the edge cache instead of origin; ALB-only design would need pre-scaled servers | OAC to S3; HTTPS only; HTTP/2+3; `/api/*` uses CachingDisabled and forwards viewer headers (incl. Authorization); WAF attached | WAF, S3 frontend, API Gateway |
| **Amazon S3 (frontend)** | Hosts the static single-page app | Cheaper and more durable than serving files from EC2/EBS, and no servers to scale | Private bucket, block public access, SSE-S3, TLS-only policy, readable only by the CloudFront distribution (OAC) | CloudFront |
| **Amazon Cognito** | Role-based sign-in (groups student/tutor/admin), issues JWTs | Managed password policy, token issuing and scaling; building auth on our own DB is a security risk and extra work | Email as username; 12+ char password policy; app client without secret, `USER_PASSWORD_AUTH`; 4 h tokens; 3 groups | API Gateway, browser |
| **Amazon API Gateway (HTTP API)** | Public API front door; verifies JWTs, throttles | HTTP API is ~70% cheaper than REST API and has a built-in JWT authorizer; an ALB would not validate tokens | `ANY /api/{proxy+}` with Cognito JWT authorizer; `GET /api/health` open; throttle 2,500 rps / burst 5,000; payload v2.0 | CloudFront, Cognito, Lambda |
| **AWS Lambda (API)** | Business logic: exams, autosave, presign, submit, release | Scales per request with no capacity planning for a spiky exam load; EC2/ECS would need pre-scaling and patching | Python 3.12, 512 MB, 15 s; in both private app subnets; X-Ray active; env vars hold only names/ARNs, no secrets; least-privilege role | API Gateway, RDS Proxy, S3, SQS, Secrets Manager |
| **AWS Lambda (workers)** | `marker` scores MCQs; `notifier` sends emails | Event-driven and pay-per-use; idle between exams, unlike always-on workers | SQS event source, batch 10, partial-batch failure reporting, max concurrency 20 (marker) / 5 (notifier) to protect the DB and SES limits | SQS, RDS Proxy, SES |
| **Amazon VPC (subnets, IGW, NAT, SGs, S3 endpoint)** | Network isolation across two AZs | Default VPC has no tiering; private subnets keep DB and compute unreachable from the internet | 10.0.0.0/16; 2 public (NAT only), 2 private app, 2 private data (no internet route); NAT per AZ; S3 gateway endpoint; SGs chain Lambda → Proxy → DB on 5432 only | Lambda, RDS Proxy, Aurora, S3 |
| **Amazon Aurora PostgreSQL (Serverless v2)** | System of record: exams, attempts, answers, scores | Multi-AZ storage (6 copies/3 AZs) and ~30–60 s failover beat single-AZ RDS; faster failover and scaling than standard Multi-AZ RDS; DynamoDB would complicate relational marking queries | Writer AZ A + reader AZ B (promotion tier 0); 0.5–8 ACU; encrypted with KMS CMK; password managed in Secrets Manager; 7-day PITR; CloudWatch log export | RDS Proxy, KMS, Backup |
| **Amazon RDS Proxy** | Connection pool in front of Aurora | Without it a Lambda burst opens thousands of connections and overloads PostgreSQL; it also reconnects to the new writer after failover | TLS required; 90% max connections; secret from Secrets Manager; subnets in both AZs | Lambda, Aurora, Secrets Manager |
| **Amazon S3 (uploads)** | Stores assignment files (PDF/ZIP ≤ 50 MB) | Cheaper and more durable (11 nines, multi-AZ) than EBS/EFS; presigned URLs keep 50 MB uploads off the API | Block public access; versioning; SSE-KMS (bucket key); TLS-only policy; lifecycle: Standard → IA 30 d → Glacier IR 180 d → expire 1,830 d; CORS POST from site only; event notification to SQS | Browser (presigned POST), Lambda, SQS, KMS |
| **Amazon SQS (+ DLQs)** | Buffers marking jobs and notification jobs | Decouples spikes from workers and retries automatically; SNS/EventBridge alone do not hold work for retry; Kinesis is overkill | Two standard queues, SSE; visibility 180 s; redrive to DLQ after 5 attempts; DLQ retention 14 days; DLQ alarms | S3, Lambda |
| **Amazon SES** | Emails tutors (new upload) and students (results released) | Cheap, deliverable bulk email; running our own SMTP is unreliable | Verified sender identity; Lambda role allowed `ses:SendEmail`; production access needed to leave sandbox | Lambda |
| **AWS Secrets Manager** | Holds the Aurora credentials | Rotatable, audited and KMS-encrypted; env vars or code would leak passwords | `manage_master_user_password` (RDS-owned secret) encrypted with the CMK; read only by Lambda role and RDS Proxy role | Aurora, RDS Proxy, Lambda |
| **AWS KMS** | Customer-managed key for data at rest | Gives key rotation, key policy and audit trails that default keys do not | Annual rotation on; used by S3 uploads, Aurora, secrets, backup vault | S3, Aurora, Secrets Manager, Backup |
| **AWS Backup** | Long-term database retention (5 years) | Central, policy-driven; automated snapshots alone expire after ≤ 35 days | Daily kept 35 d; monthly kept 1,825 d; encrypted vault | Aurora, KMS |
| **Amazon CloudWatch (+ X-Ray, SNS)** | Logs, metrics, dashboard, alarms, traces | Native, no agents for Lambda/API/RDS/SQS; third-party tools add cost and setup | 30-day log retention; alarms on API 5xx, Lambda errors, both DLQs, DB CPU → SNS email; dashboard; X-Ray active tracing | All services, SNS |
| **AWS IAM** | Least-privilege permissions | Roles with temporary credentials instead of access keys | One Lambda role (scoped to named bucket/queues/secret/key); RDS Proxy role; Backup role; GitHub OIDC role | All services |
| **GitHub Actions** | CI/CD pipeline: test, build, plan, apply on push to `main` | Lives with the code; OIDC removes stored AWS keys; CodePipeline would add a second system to manage | Jobs: compile + `fmt -check` → build Lambda → `init` → `validate` → `plan` → `apply` (main only) → CloudFront invalidation → smoke test | IAM (OIDC), Terraform, S3 state |
| **Terraform (+ S3 state)** | Infrastructure as code for the whole stack | Reproducible, reviewable and portable; console building is not repeatable, and CloudFormation locks us to one cloud | AWS provider 5.x; versioned, encrypted S3 backend with lockfile; `bootstrap/` stack creates state bucket + OIDC role | All AWS services |
| **AWS CloudFormation (Free Plan)** | Creates the live Aurora Express cluster | CloudFormation exposes the Express creation setting that the Terraform AWS provider lacks | Terraform manages a stack with `WithExpressConfiguration` enabled. The cluster has one writer, AWS-owned encryption, and IAM database authentication over TLS | Terraform, Aurora, IAM, Lambda |

The Aurora, RDS Proxy, and database secret rows describe the production design. The live Free Plan deployment connects Lambda directly to Aurora Express over TLS using short-lived IAM database tokens.
